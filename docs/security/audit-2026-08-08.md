## HIGH

### H1 — `totp_secret` readable by the app role and fetched on every user lookup (known backlog item, still open)

- Where: DB grant `SELECT(totp_secret)` to `factory_app` on `users`; full-row selects in `packages/core/src/identity/enrolment.ts:16,36,53` and `packages/core/src/identity/magic-link.ts:74-77` (`db.select().from(users)`).
- Problem: any SQL injection, ORM bug, or over-broad serialization of a user object leaks the shared TOTP secret, permanently defeating 2FA for that user.
- Exploit: an endpoint that returns the user row (e.g. a future profile API) serializes `totpSecret`; attacker with a phished magic link now mints valid TOTP codes forever.
- Remediation: revoke `SELECT(totp_secret)` from `factory_app` default reads — dedicated `SECURITY DEFINER` accessor or explicit column list everywhere — or encrypt the secret at rest; select explicit columns in identity code.

### H2 — No rate limiting on auth endpoints (known backlog item, still open)

- Where: `packages/core/src/identity/magic-link.ts:24` (`requestMagicLink`), `enrolment.ts:48` (`verifyUserTotp`), `enrolment.ts:29` (`confirmTotpEnrolment`).
- Problem: unlimited magic-link requests per email/IP (mail-bomb + Resend cost abuse) and unlimited TOTP guesses (6 digits, ±1 step window → ~1e6/3 effective space, brute-forceable online).
- Exploit: attacker with a stolen unexpired magic link (or a session at the TOTP gate) scripts TOTP guesses; at even 10 req/s the 90-second window gives meaningful success probability over repeated logins.
- Remediation: Redis-backed limiter (Redis is now in the chassis via the Deadline engine): magic-link ≤3/15min per email + per-IP cap; TOTP ≤5 attempts then lockout/backoff, per OWASP ASVS 2.2.1.

## MEDIUM

### M1 — TOTP replay: same code accepted repeatedly within its window (known backlog item, still open)

- Where: `packages/core/src/identity/totp.ts:58-70` (`verifyTotp`), no last-used-step storage; `enrolment.ts:48-56` passes straight through.
- Problem: a code observed in transit (shoulder-surf, phishing proxy, log capture) is reusable for up to ~90s (step ±1 skew), violating ASVS 2.8.4 single-use.
- Exploit: real-time phishing proxy relays the victim's code to its own login within the window and gets a second valid session.
- Remediation: store `totp_last_used_step` on `users`; accept a code only if its step > last used, updated with a conditional UPDATE.

### M2 — Dependency: esbuild <=0.24.2 (moderate, GHSA-67mh-4wv8-2f99)

- Where: `esbuild@<=0.24.2` via `packages/core > drizzle-kit > @esbuild-kit/*`; patched >=0.25.0.
- Problem: esbuild dev server accepts cross-origin requests, letting any website read responses.
- Reachability: dev-only toolchain (drizzle-kit migrations); the esbuild dev server is never started in production and drizzle-kit is not a runtime dep — effective risk on the deploy target is nil, but the baseline mandates patching.
- Remediation: bump `drizzle-kit` to a release off the deprecated `@esbuild-kit` loaders (>=0.31), or add a pnpm override `esbuild>=0.25.0`. Non-breaking for a dev tool; apply on the next remediation branch. drizzle-kit/esbuild ship ARM binaries — no ARM concern.

## LOW

### L1 — No TOTP disable/recovery path

- Where: `packages/core/src/identity/enrolment.ts:19-20` throws "TOTP already enabled; disable it first", but no disable function exists anywhere in the module.
- Problem: lost-device recovery requires manual DB surgery; when a disable path is added it must require step-up auth and revoke sessions, or it becomes the 2FA bypass.
- Remediation: implement disable gated on a valid current TOTP code (or documented owner-verified support flow) + `revokeAllSessions`; add recovery codes.

### L2 — Enabling TOTP does not revoke pre-existing sessions

- Where: `enrolment.ts:37` (`confirmTotpEnrolment` only flips `totp_enabled`).
- Problem: sessions issued before 2FA enrolment (potentially attacker-held, the very reason a user enables 2FA) remain valid for up to 30 days.
- Remediation: call `revokeAllSessions` (except current) on enrolment confirmation.

### L3 — 30-day fixed session TTL, no idle timeout or rotation

- Where: `packages/core/src/identity/sessions.ts:8` (`SESSION_TTL_DAYS = 30`).
- Problem: a leaked cookie is valid for a month regardless of activity; no re-issue on privilege change. (No session fixation: tokens are 256-bit server-generated post-auth, never adopted from the client — that check passes.)
- Remediation: add idle expiry (e.g. 7 days sliding) and rotate on role change; acceptable to defer pre-launch.

### L4 — `stripe_events` lacks the append-only trigger the other immutable tables have

- Where: DB — `audit_log`, `evidence`, `record_versions` have BEFORE UPDATE/DELETE triggers; `stripe_events` relies only on the absence of UPDATE/DELETE grants, and its RLS policies are `true` (global table).
- Problem: defence-in-depth gap; a future grant widening would silently make the webhook idempotency ledger mutable.
- Remediation: attach the existing `append_only()` trigger to `stripe_events`.

## Clean checks (detail)

- Magic link: 256-bit `randomBytes` token, SHA-256 hash-only storage, 15-min TTL, race-safe single-use consume (`magic-link.ts:60-73`) — good. Uniform create-on-first-sight flow avoids account enumeration.
- TOTP primitive: RFC 6238, 160-bit secret, constant-time compare, ±1 step only — good apart from M1.
- Role enforcement: `requireRole`/`requireWriteAccess` with auditor hard-excluded from writes (`roles.ts`), backed by RLS (`FORCE` on all tenant tables) and column-level grants — good.
- Billing webhooks: `verifyWebhookSignature` fails closed when `STRIPE_WEBHOOK_SECRET` unset; handle-then-mark idempotency with documented at-least-once semantics; durable `stripe_events` store. `InMemoryProcessedEventStore` must remain test-only.
- Permission baseline: no UPDATE/DELETE grants on `audit_log`; UPDATE limited to intentional columns (session revocation, TOTP flags, subscription mirror, obligation/checklist state). `users`/`sessions`/`magic_link_tokens` have RLS off — accepted pre-auth deviation, recorded in the snapshot.
- Working tree included the uncommitted deadlines module; nothing adverse found there in the scanned passes.
